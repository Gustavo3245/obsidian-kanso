# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- `manifest.json` must only contain fields from Obsidian's theme manifest schema (`name`, `version`, `minAppVersion`, `author`, `authorUrl`); there is no `description` field, and Obsidian's theme review flags unknown fields. `scripts/validate-json.mjs` enforces the required-field list, so keep it in sync with the schema, not with whatever fields happen to be present.
- To reproduce Obsidian's community-theme review CSS lint locally (not just this repo's `.stylelintrc.json`), lint with the `stylelint-config-obsidianmd` package instead — it is the same config referenced by `obsidianmd/obsidian-sample-theme`. Its `plugin/no-unsupported-browser-features` rule flags CSS features (e.g. `css-masks`) unsupported by old Chromium on *both* the unprefixed and any vendor-prefixed declaration, so adding a `-webkit-` fallback does not clear that warning by itself; the fix is to raise `minAppVersion` past the Chromium version that gained full support, or avoid the feature.
- CI (`.github/workflows/validate.yml`) runs `npm run validate` (manifest/variant JSON shape) and `npm run lint:css` (this repo's own relaxed `.stylelintrc.json`, not the stricter official config above).
- Each dark/light variant's `--kanso-*` overrides live in `theme.css` near the `@settings` block (around line 70 on `main`). A new variant needs: an entry in the `@settings` class-select list, a selector-list addition so `.theme-light.<variant>` forces the dark palette, a `.theme-dark.<variant>, .theme-light.<variant> { --kanso-bg0..bg4 }` block (match that compound-selector specificity, not a bare `.<variant>` rule, or the base block's `.theme-light.<variant>` entry silently wins and the variant falls back to Zen's colors when forced while Obsidian itself is in light mode), a `:not(.<variant>)` addition to the Pearl/light fallback selector, and (for dark variants) an addition to the `.theme-light.<dark-variants>` accent block. Also add `variants/<variant>.json` (`{"class","name","mode"}`) for Obsidian's variant picker.
- To visually test `theme.css` in a real Obsidian when no FUSE/X server is available: extract the AppImage (`./Obsidian.AppImage --appimage-extract`, since mounting needs FUSE), then run the extracted `squashfs-root/obsidian` binary with `--no-sandbox --ozone-platform=headless --enable-features=UseOzonePlatform --ozone-override-screen-size=WIDTH,HEIGHT --remote-debugging-port=PORT --user-data-dir=<profile>`. Plain `--headless` or `--window-size` do not produce a usable framebuffer; the actual window size instead comes from `<profile>/<vault-id>.json`'s `width`/`height` fields (edit that file, or rely on `--ozone-override-screen-size`, for a usable viewport). Register the test vault once by writing `<profile>/obsidian.json` with `{"vaults":{"v1":{"path":"<vault>","ts":<ms>,"open":true}}}` before first launch, so it opens straight into the vault instead of the picker. Drive it with `chrome-devtools-axi`, using your own `--remote-debugging-port`/`--user-data-dir` and a unique `CHROME_DEVTOOLS_AXI_SESSION`, since concurrent Kanso tasks run their own Obsidian instances and the tool's default session/port is shared. Switch themes/variants from the console with `app.customCss.setTheme('Kanso')` and `document.body.classList.add(...)`. `emulate --viewport` has been observed to break subsequent `screenshot` calls in this headless setup, prefer sizing the real window instead; also, the window chrome (the native title-bar button row specifically) can render a stale/cached frame in screenshots that does not reflect live DOM changes, so verify title-bar CSS via `getComputedStyle`/`pointerEvents` in `eval` rather than trusting that one region of a screenshot.
